# Изолированная установка WantedFrame MCP

Этот комплект содержит только `integrations`. Он не заменяет приложение, рынок,
TGPT, Infra Control, MAX или общий конфиг прокси. Скрипт подготовки не запускает
сервис. Приватный конфиг, pairing и снимки создаются вне исходников и архива.

## Что требуется от оператора

- Отдельный HTTPS hostname с DNS на MAIN и доступ к действующему TLS-прокси.
- Отдельный GitHub OAuth App: callback `https://HOST/auth/callback`, client ID и secret.
- Числовой GitHub ID владельца (в CLI предложен `159386897`; проверить владельца).
- Точный callback OAuth из настроек подключения ChatGPT для `redirectUris`.
- Разрешённый способ доставить архив и выполнить установку только этого сервиса.

Пароль Warframe не используется. Secret вводится скрыто через CLI на VPS; не
передавать его в командной строке, чате, журнале или публичном репозитории.

## Комплект и подготовка

В Windows из корня репозитория (Python 3.12+):

```text
python integrations/deploy/package.py --output .tmp/wantedframe-integrations.tar.gz
```

Архив строится по явному списку файлов; произвольные файлы рядом с кодом туда не
попадают. Он содержит ревизию Git и SHA-256 каждого исходника; manifest учитывает
локальные изменения. SHA-256 самого архива выводится без приватных данных.
Перед установкой сравнить этот SHA-256 после доставки. На Linux извлечь архив
в отдельный каталог, проверить `sha256sum --check MANIFEST.sha256` и выполнить:

```sh
sudo bash deploy/prepare-host.sh
```

Скрипт требует Python 3.12+, создаёт пользователя без shell, venv в
`/opt/wantedframe-mcp`, приватные каталоги `/etc/wantedframe-mcp` и
`/var/lib/wantedframe-mcp`, устанавливает один systemd unit и сохраняет точный
`pip freeze`. При наличии этих путей он останавливается: обновление действующей
установки требует отдельного осмотра, без удаления данных или общего перезапуска.
Код и venv остаются у root; сервис может записывать только своё состояние и сокет.

## Приватная конфигурация

Создать pairing в каталоге владельца сервиса, чтобы shell не показывал секреты:

```sh
sudo -u wantedframe-mcp /opt/wantedframe-mcp/venv/bin/wantedframe-mcp init \
  --config /etc/wantedframe-mcp/config.json \
  --pairing /var/lib/wantedframe-mcp/wantedframe-pairing.json
```

Проверить владельца и права `0600` обоих файлов. Pairing нужен только WantedFrame
на Windows; его не прикладывают к чату и не используют как OAuth-токен MCP.
Доставить его приватным каналом, импортировать в приложение и удалить транспортную
копию по решению владельца. `ingestToken` работает только для отправки на `/ingest`.

## HTTPS-прокси

Для прокси на хосте оставить `listenHost=127.0.0.1` и `listenPort=18767`.
`nginx.conf.example` содержит отдельный hostname, лимит тела 24 MiB и общий лимит
запросов. Пути сертификатов и hostname заменить перед добавлением конфигурации.
`Caddyfile.example` показывает минимальный hostname блок; общий rate limit следует
взять из существующей политики прокси. Стандартный Caddy не имеет встроенного
rate limiter. Не считать этот минимум полной настройкой защиты от потока запросов.

Для Docker-прокси использовать фиксированный Unix socket:

- В приватном `config.json` добавить `"listenUds":"/run/wantedframe-mcp/web.sock"`.
- Смонтировать только `/run/wantedframe-mcp` в контейнер прокси, например по тому же
  пути; Caddy upstream: `unix//run/wantedframe-mcp/web.sock`.
- Выдать процессу прокси доступ только к группе `wantedframe-mcp` для каталога
  сокета. Не выдавать доступ к `/etc/wantedframe-mcp` или `/var/lib/wantedframe-mcp`.
- Проверить владельца каталога и сокета и членство процесса прокси в группе.

`uvicorn` задаёт сокету `0666`, поэтому границей доступа служит сам каталог
`/run/wantedframe-mcp` с правами `0750`: пройти к сокету могут только владелец
и эта узкая группа. Не монтировать сокет отдельно в общедоступный каталог и
не менять права каталога на `0777`. Если политика MAIN требует именно `0660`
на самом сокете, согласовать отдельную настройку после фактического старта.
Слепой `ExecStartPost=chmod` не подходит: у `Type=simple` он может выполниться
до создания сокета.
Не публиковать порт 18767 и не открывать приложение на `0.0.0.0`.

Проверить конфиг штатной командой прокси. Применить reload только после успешной
проверки; не выполнять общий restart Docker или VPS. Затем:

```sh
sudo systemctl enable --now wantedframe-mcp.service
curl --fail --silent --show-error https://HOST/healthz
curl --fail --silent --show-error https://HOST/.well-known/oauth-authorization-server
```

`healthz` и OAuth discovery подтверждают доступность, но не передачу аккаунта или
OAuth вход владельца. Внешний `/mcp` должен отклонять запрос с ingest-токеном.
Проверки с токеном делать из приватного клиента; не печатать его в shell.

## Одна практическая приёмка

После подключения WantedFrame в ChatGPT пройти реальный цикл, сохранив только
необходимые результаты и даты:

1. Снять данные настоящего аккаунта и вручную отправить из GUI.
2. `get_account_overview`, затем `list_data_sections`: проверить время инвентаря,
   время получения, привязку, `missing`, `partial`, `unmappedCollections` и
   `omittedFields`. Регистрация раздела не означает, что источник его заполнил.
3. Найти один ресурс, прочитать количество и сверить с игрой.
4. Найти одно оружие и прочитать `/configs/0/mods` через `get_record` на той же
   ревизии. Null и отсутствующее поле не подменять нулём.
5. Прочитать одну запись производства, если источник её действительно отдаёт.
6. После реального изменения получить и отправить повторный снимок. Проверить
   новую ревизию/дату и изменённое количество; сравнение запрещено для manual.

Синтетическая фикстура полезна для регрессии, но не доказывает проверку в игре.
Расширение схемы допускается лишь по найденным разрешённым полям реального
источника; сырые секреты не отправлять. Не сохранять полный аккаунт в отчёте.

## Остановка или отзыв

Отключить синхронизацию в GUI и удалить подключение ChatGPT. Для отзыва upload
заменить `ingestToken`, приватно пересоздать pairing, перезапустить только
`wantedframe-mcp.service`. Для удаления снимков остановить только этот сервис и
удалить только `/var/lib/wantedframe-mcp/snapshots.json` после решения владельца.
OAuth-состояние и уже переданные в ChatGPT данные требуют отдельного отзыва.
Не очищать общий Docker и не удалять данные соседних сервисов.
